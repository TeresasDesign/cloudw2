1. Explain the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment.

Continuous Integration (CI) is all about developers frequently merging their code changes into a shared repository, where automated builds and checks run right away to catch bugs early. Continuous Delivery takes it a step further by ensuring the code is always fully built, tested, and ready to go, though a human still manually clicks a button to approve the final release to production. Continuous Deployment fully automates that final step—every single code change that passes the automated pipeline goes straight to production with zero human intervention. For example, in our project, CI tests our builds on every push, while an automated deployment pipeline pushes updates straight to our Rahti environment without needing manual terminal commands.

2. Describe the structure of a GitHub Actions workflow (triggers, jobs, steps). What would a minimal pipeline for the app you built in Week 4/5 need to do?

A GitHub Actions workflow is structured hierarchically using three main parts: triggers (on), which define when the workflow runs (like on every push to the main branch); jobs, which group execution steps together; and steps, which are the individual commands run sequentially on a virtual runner. For our web app, a minimal pipeline needs to check out the repository code, log into the GitHub Container Registry (GHCR) to build and push the container image, securely authenticate with OpenShift using tokens, and run oc set image to update the running deployment on Rahti.

3. Explain the difference between a liveness probe and a readiness probe in Kubernetes/Rahti. What happens when each one fails?

Both are automated health checks used by Kubernetes, but they have completely different jobs. A liveness probe checks if the application container is still healthy and running properly; if it fails repeatedly, Kubernetes assumes the app is deadlocked or crashed, kills it, and automatically restarts the pod. A readiness probe checks if the app is fully initialized and actually ready to handle user traffic (like making sure it has successfully connected to the database). If a readiness probe fails, Kubernetes doesn't restart the pod, but instead temporarily pulls it out of the service load balancer so users aren't sent to an unready instance.

4. Why should secrets (registry tokens, cluster login tokens) never be hard-coded into a CI/CD pipeline file? How does GitHub Actions handle this instead?

Hard-coding sensitive credentials like cluster tokens or registry passwords directly into pipeline files is a major security risk because anyone who can view your repository can steal them and access your cloud infrastructure. Instead, GitHub Actions provides an encrypted vault called Repository Secrets. The workflow file references these secrets securely at runtime (using expressions like ${{ secrets.OPENSHIFT_TOKEN }}), passing them to the environment dynamically without ever exposing them in the plain-text source code or git history.
