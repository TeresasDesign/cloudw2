What is Infrastructure as Code, and which problems of manually created infrastructure does it solve? Use your own Week 1 VM setup as an example.

Infrastructure as Code (IaC) is the practice of managing and provisioning computing infrastructure using human-readable configuration files rather than manual clicking through web dashboards or configuring physical hardware. IaC solves major problems of manual infrastructure, such as human error, lack of documentation, and the inability to easily reproduce environments. For example, in Week 1, setting up your virtual machine on cPouta required manually logging into the web dashboard, selecting an image and flavor, clicking through network and security group settings, manually attaching a floating IP, and configuring Nginx over SSH. If you needed to recreate that exact setup later, you had to remember every single manual click. With OpenTofu, that entire process is defined in code files like main.tf and deployed automatically in minutes with zero guesswork.

What is the state file used for? Why should it not be committed to a Git repository, and how do teams usually share it instead?

The state file (terraform.tfstate) is OpenTofu's internal database and "single source of truth." It maps your real-world cloud resources in cPouta to the resource blocks declared in your configuration files, tracking IDs, metadata, and dependencies. It should not be committed to a Git repository because it often contains sensitive data, credentials, or secrets in plain text. Furthermore, committing state files in Git leads to severe merge conflicts and race conditions when multiple team members apply infrastructure changes simultaneously. Instead, teams share state files using remote backends (such as AWS S3, Terraform Cloud, or Object Storage) that support state locking, ensuring only one person can modify the infrastructure at a time.

What is configuration drift, how does it happen, and how does an IaC tool detect it?

Configuration drift occurs when the real-world state of your cloud infrastructure diverges from the desired configuration defined in your code. This usually happens when an administrator makes manual "hotfixes" or edits directly through a cloud provider's web console or CLI—such as manually deleting a firewall rule in the cPouta dashboard, which we tested in Experiment 2. An IaC tool detects drift during the tofu plan phase. OpenTofu queries the cloud provider's API to inspect the actual live resources, compares them against the recorded state file and configuration, and flags any unexpected differences (such as missing or modified security rules).

Some changes in a tofu plan are made in place, while others require the resource to be destroyed and re-created. Why does this matter, and what kinds of changes would you be especially careful with?

This distinction matters because destroying and re-creating a resource can cause downtime, service interruption, or permanent data loss. For instance, modifying a VM's user_data script or changing an immutable cloud property forces OpenTofu to destroy the old instance and spin up a new one, which can result in a new public IP address or lost local files. You should be especially careful with changes that trigger recreation on stateful resources, such as production databases, persistent storage volumes, or core networking gateways. In a production environment, wiping a database or dropping a primary storage volume to update a configuration parameter would cause catastrophic data loss unless proper backups, replicas, or decoupling strategies (like separating app servers from storage volumes) are in place.
