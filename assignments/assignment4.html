1. System Architecture

  • Frontend: Nginx (nginxinc/nginx-unprivileged:alpine) listening on port 8080.
  • Backend: Python (Gunicorn) REST API.
  • Database: MySQL (appdb) with a PersistentVolumeClaim (PVC) mounted to /var/lib/mysql.

2. Validation Experiments

  1. Database Persistence:
    • Action: Deleted MySQL Pod (oc delete pod -l app=mysql).
    • Result: Visitor counter persisted after the MySQL Pod was recreated, demonstrating persistence through the network-attached PVC.
  2. Pod Recovery (Self-Healing):
    • Action: Deleted backend Pod (oc delete pod <pod-name>).
    • Result: Kubernetes ReplicaSet automatically spawned a replacement Pod with zero app downtime.
  3. Horizontal Scaling:
    • Action: Scaled backend to 3 replicas (oc scale deployment/backend --replicas=3).
    • Result: Kubernetes Service automatically load-balanced traffic across all 3 active Pods using label selectors.
  4. Rolling Update:
    • Action: Triggered rollout (oc rollout restart deployment/frontend).
    • Result: Kubernetes incrementally replaced Pods with zero downtime via RollingUpdate strategy.

3. Key Troubleshooting Points

  • Nginx Non-Root Execution: Default Nginx fails due to Rahti’s non-root security policy. Resolved by using nginxinc/nginx-unprivileged:alpine on port 8080.
  • ConfigMap Mounting: Overriding /etc/nginx/nginx.conf broke core directives. Resolved by mounting custom proxy routes into /etc/nginx/conf.d/default.conf.
  • Data Persistence: Default Pod storage is ephemeral. Resolved by binding a PersistentVolumeClaim to /var/lib/mysql.
  • Frontend/API Routing: Nginx proxies requests under /api/ to the backend service on port 8000.

4. Rahti vs. Docker Compose + cPouta

Feature Rahti (PaaS) cPouta + Docker (IaaS)
Management Fully managed OS and Kubernetes cluster by CSC Manual OS patching, firewall, and VM management
Self-Healing Automatic multi-node Pod recovery via ReplicaSets Limited to container restarts within a single VM
Scaling Declarative single-command multi-node scaling (oc scale) Manual setup, hard-capped by single VM capacity
Storage Network PVCs independent of physical nodes Local Docker volumes tied to host filesystem
